### BUG 2 — ICP Setup Page Spins Forever

**ROOT CAUSE: `setLoading(false)` is never called when the API call to `/icps` hangs or throws after the `try` block but before the catch**

Looking at `apps/portal/src/app/(dashboard)/dashboard/leads/icp/page.tsx:142-153`:

```ts
supabase.auth.getSession().then(async ({ data: { session } }) => {
  if (!session) { setLoading(false); return }
  setToken(session.access_token)
  try {
    const res = await api.get<{ data: ICP[] }>('/icps', session.access_token)
    setIcps(res.data || [])
  } catch (err) {
    setLoadError(...)
  }
  setLoading(false)       // ← line 152: only reached if try/catch completes
}).catch(() => setLoading(false))
```

The structure looks safe at first glance — `setLoading(false)` at line 152 is outside the `try/catch` so it runs whether the API call succeeds or throws. **However**, there is a critical scenario: if `api.get('/icps', ...)` never resolves (i.e., the Railway API is down, or the request hangs indefinitely with no timeout), the `await` on line 147 hangs forever. The `.catch` on line 153 only handles a rejection of the outer `.then()` promise — a hanging fetch inside an `async` `.then()` callback is not covered by that outer `.catch()`. The `setLoading(false)` at line 152 is only reached when the `await` resolves or rejects.

- `apps/portal/src/lib/api.ts:4` — `apiFetch` calls `fetch(...)` with no timeout option; if `NEXT_PUBLIC_API_URL` is misconfigured or Railway is down, the fetch hangs until the browser's default timeout (up to 300 seconds)
- `apps/portal/src/app/(dashboard)/dashboard/leads/icp/page.tsx:147` — the hanging fetch

**FIX NEEDED:** Add an `AbortController` timeout to `apiFetch` in `apps/portal/src/lib/api.ts`, e.g. 15 seconds. This will cause the fetch to reject instead of hanging, the `catch` block will run, `setLoadError` will be set, and `setLoading(false)` at line 152 will fire.
