## Performance Impact

**Negligible.** Here's why:

- The portal already uses Tailwind CSS. Dark mode in Tailwind is a single config flag (`darkMode: 'class'`) — it adds CSS classes, it doesn't add a new stylesheet or extra network request.
- The visual changes in Option B (gradients, shadows, spacing, hierarchy) are all CSS-only. No new dependencies, no JavaScript weight added.
- The sidebar grouping and dashboard hero are layout restructures — same number of DOM nodes, just reorganised.
- The "Today" bar is server-rendered (the dashboard page is already `force-dynamic`) — no extra API calls, it uses data already being fetched.

The only thing that could affect performance is if we added a **heavy animation library** (like Framer Motion). We won't. All transitions stay CSS (`transition-all`, `duration-200`). Same as what's there now.

**Net performance change: zero.**

---

## Risk

There are three real risks, all manageable:

**1. Dark mode state persistence — low risk, known solution**
Dark mode needs to remember the user's preference. The standard approach is `localStorage` + a class on `<html>`. The only gotcha is a flash of the wrong theme on page load (FOUC). Fix is a one-line inline script in `<head>` that runs before React hydrates. Completely standard, well-documented.

**2. Every component needs dark mode classes — medium effort, low risk**
Tailwind dark mode means every `bg-white` needs a `dark:bg-gray-900`, every `text-gray-900` needs a `dark:text-white`, etc. This is the bulk of the work. It's tedious, not technically risky. If we miss a spot, the worst case is one card looks wrong in dark mode — not a breakage.

**3. The dashboard restructure touches shared components — low risk**
`StatCard`, `ProductCard`, `Sidebar` are used in multiple places. Any change to them affects every page that uses them. But these components are small and self-contained — easy to audit. No database changes, no API changes, no auth changes involved.

**What this does NOT touch:**
- No API routes
- No database schema
- No authentication
- No billing logic
- No Supabase queries
- No environment variables

If something looks wrong after the build, a single git revert brings back the old look instantly. The risk ceiling is "a page looks off" — not "something breaks for a client."
