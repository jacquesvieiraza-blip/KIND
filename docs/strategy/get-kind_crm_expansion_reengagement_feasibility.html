Get-Kind — CRM Expansion & Re-Engagement Feasibility Verification

Purpose: ask Claude Code to verify whether the current Get-Kind architecture can support native client CRM connectivity after launch, without implementing it now.

Planned action point: Post-launch — 25 August 2026.

1. Current product position

Get-Kind currently supports client lead ingestion through CSV, but does not currently have native plumbing to connect to a client's CRM.

Closed Won

Potential future use: identify existing customer accounts and relevant contacts for expansion campaigns, subject to the client's instructions, data minimisation, suppression and the applicable outreach rules.

Closed Lost

Potential future use: identify previously lost opportunities that may be suitable for re-engagement, subject to loss reason, timing/cool-down, suppression, prior objections and the global contact-permission engine.

Do not assume “Closed Lost” means “safe to contact again”.

Lost opportunities must not be recycled automatically if the record shows an opt-out, do-not-contact instruction, legal restriction, unsuitable loss reason, or any other suppression condition.

2. Recommended product boundary

The initial CRM integration should be considered a read-only ingestion and segmentation capability, not a bidirectional CRM replacement.

CLIENT CRM
   ↓
read authorised records
   ↓
normalise account / contact / opportunity status
   ↓
deduplicate against Get-Kind
   ↓
apply suppression + compliance rules
   ↓
segment:
   CLOSED WON → expansion candidate pool
   CLOSED LOST → re-engagement candidate pool
   ↓
client approves campaign
   ↓
existing Get-Kind campaign / sequence / meeting-booking engine

Write-back to the CRM can be evaluated later. It is not required for the first useful version.

6. Hard exclusions for re-engagement

Claude is not being asked to determine legal sufficiency. It should verify whether the architecture can enforce hard exclusions before a Closed Lost record becomes campaignable.

  • explicit unsubscribe / opt-out;
  • client DNC instruction;
  • employer floor suppression;
  • prior objection to marketing;
  • unknown / blocked jurisdiction under the global permission framework;
  • loss reason that the client marks as permanently unsuitable;
  • contact has left the account and identity cannot be safely refreshed;
  • cool-down period has not expired;
  • duplicate active opportunity / active client conversation.

7. CRM should remain the system of record

Recommended architecture:

The client's CRM remains authoritative for account, opportunity and sales-stage state. Get-Kind consumes only the data required to select and run campaigns.

CRM = system of record for:
- accounts
- contacts
- opportunities
- won/lost state
- loss reason
- client ownership

GET-KIND = system of action for:
- sourcing
- enrichment
- compliance gating
- campaign selection
- sequencing
- reply handling
- booking meetings

8. Sync model Claude should assess

Claude should compare three possible integration approaches against the current codebase.

ModelDescriptionWhat Claude should assess
A. Scheduled pull Get-Kind periodically reads changed CRM records through the CRM API. Existing job scheduler, token handling, rate limits, incremental cursors, idempotency.
B. Webhook + reconciliation CRM sends change events; Get-Kind periodically reconciles as a safety net. Webhook authentication, retry handling, event dedup, background jobs.
C. Manual sync / CSV bridge Existing CSV model becomes an interim post-launch feature while native connectors are developed. Whether CSV importer can accept opportunity status/loss reason/external IDs with minimal architecture change.

Claude should recommend which approach best fits the existing architecture, but must not implement it.

11. Matching and deduplication

Claude should inspect the current CRM dedup logic already used before enrolment and determine whether it could support a native sync.

Verify potential matching keys and collision handling:

CRM external ID        → strongest within one client
email                   → person identity candidate
company domain          → account identity candidate
name + company          → weaker fallback
existing lead ID        → Get-Kind identity
Client-scoped identity matters.

A CRM external ID from Client A must never resolve to Client B's data. Existing Nexus/RLS protections should be reviewed for this path.
