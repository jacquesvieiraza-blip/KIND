Purpose: read-only Claude Code verification of whether the current Get-Kind architecture can support a future Social Intent layer across LinkedIn, X/Twitter, Instagram/Meta and similar approved sources.

Goal: detect people or companies showing relevant commercial intent, then pass them into the existing Get-Kind enrichment, compliance, sequencing and meeting-booking machinery.

2. Product objective

Get-Kind currently relies primarily on identity/contact providers such as PeopleDataLabs, Apollo and Hunter. The proposed Social Intent layer is different: it is intended to detect who appears interested now, then resolve and enrich only the most relevant people.

Social should contribute signals, not replace identity providers.

10. Client-owned vs public intent

The system should distinguish social events by relationship to the client.

CLIENT-OWNED ENGAGEMENT
- comment on client's post
- message to client's account
- client's lead form
- client's event registration

PUBLIC INTENT
- public post mentioning problem
- public post asking for recommendation
- public competitor dissatisfaction
- public category discussion

Claude should verify whether such source context can be represented so the global compliance engine can treat the routes differently later.

13. Compliance and platform-safety boundary

Social discovery must not bypass the existing global permission framework.

A social event can increase priority or reveal intent, but it must not itself be treated as automatic permission to contact through another channel.

Verify whether future social leads can still pass through:

source provenance
→ jurisdiction resolution
→ recipient type
→ channel selection
→ contact permission
→ suppression
→ FIGSY
→ campaign
→ send

Also verify that there is no current architectural assumption that a discovered email or verified email automatically means outreach is allowed.

14. Do not build a scraping dependency

Claude should verify whether any current or planned social integration code depends on browser scraping, credential sharing, session-cookie automation or other brittle unofficial access patterns.

Target architecture: approved APIs, authorised client connections, or other contractually permitted data sources.

If scraping-oriented code exists, report it separately as a platform-risk finding. Do not expand or implement it.

16. Required feasibility questions

  1. Does the current repository already contain social-platform code, environment variables, SDKs or unused integrations?
  2. Is there an existing provider/connector abstraction suitable for social sources?
  3. Can per-client OAuth credentials be stored securely?
  4. Can one client connect multiple social accounts/pages?
  5. Can authenticated webhooks be received per client?
  6. Can events be processed idempotently?
  7. Can scheduled API polling run safely?
  8. Can incremental cursors/checkpoints be stored?
  9. Can rate limits and retries be handled?
  10. Can social events be stored separately from leads?
  11. Can unresolved social actors exist without becoming lead records?
  12. Can a social event later link to a resolved person/company?
  13. Can multiple social identities link to one person?
  14. Can provenance and source URL/reference be preserved?
  15. Can event timestamps be preserved for recency scoring?
  16. Can current AI classification infrastructure classify social text?
  17. Can current scoring infrastructure ingest a social intent score?
  18. Can FIGSY consume multiple signals for one prospect?
  19. Can the system distinguish inbound social interest from public intent?
  20. Can the global permission gate receive social-source provenance?
  21. Can opt-out/suppression block outreach even when social intent is high?
  22. Can social-triggered campaigns still use the existing sequence engine?
  23. Can a booked meeting be attributed to a social event?
  24. Can source cost / API cost be attributed to social-origin meetings?
  25. Is there any current scraping dependency that would create platform risk?
  26. Can this capability be added without modifying the core send path?
